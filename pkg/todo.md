# concx 定位与候补能力（TODO）

本文整理仓库目标定位、范式边界，以及可纳入考虑的后续方向。  
原则： **对外是少数有范式约束的能力包；策略与调参是选项，不是并列原语包。**

**核心三包（当前能力面）：** `nest`（生命周期）、`schedx`（编排）、`chanx`（通信，`pkg/chanx`；`x/chanx` 已 archived）。  
能用它们的范式接口 / 选项 / 具名糖表达的，就在这三包内提供；只有组合仍盖不住时，才走扩展闸门（见 §2.1）。


---

## 1. 仓库定位

**concx = 与 goroutine 协作相关的「受约束并发」工具箱。**

- 管生命周期、通信、编排（及未来同级范式）
- 不是业务框架，也不替代 `x` 中的通用容器 / `syncx`
- 不是 `singleflight`、令牌桶、Barrier 等原语的拼盘；这类能力若需要，落在某范式包的 `With*` 上

判据（是否进本仓）：

- 离开 goroutine / context / 取消 / 背压后，该抽象是否仍有独立意义？
    - 纯数据结构（queue/stack/map）→ 留 `x`
    - 必须涉及协作与取消才有意义 → 可进 concx

## 2. 产品纪律：范式包 vs 选项

| 层级       | 含义                                                 | 例子                                                    |
|------------|------------------------------------------------------|---------------------------------------------------------|
| 范式能力包 | 用户面对的一种完整用法与心智模型；小 API 表面 + 选项 | `nest`、`Scheduler`、未来的 `chanx` / Actor / Future    |
| 选项       | 同一范式下的策略、容量、模式、策略钩子               | `WithMaxPending`、`WithParallel`、FIFO/LIFO、限流、超时 |

示例（编排，不是新包）：

- 严格一个个顺序执行 → `WithParallel(1)` + 合适的 pending（如 `WithMaxPending(1)`）
- Pipeline → 编排的一种拓扑 / 模式，当前仅 FIFO / LIFO，可后续扩展为更多 `mode`
- 信号、频率限制、令牌桶 → 背压 / 准入选项，不单独对外成包

立新范式包前问三句：

1. 用户口头是否在要一种完整用法（「我要 Actor / Future」），而不是「加个限流」？
2. API 能否收成很小表面 + `With*`？
3. 若只做成现有包的选项，主叙事是否说不清？

三句都偏「是」→ 新范式；否则 → 选项。

### 2.1 扩展闸门（相对 nest / schedx / chanx）

默认路径：

```
具体场景
  → 能否用三包的范式 API 直接表达？     → 能：提供（含选项）
  → 能否用选项组合表达？               → 能：选项；高频则具名糖
  → 再怎么组合仍不满足？               → 进入下面三问
```

三问（建议按序）：

1. **三包是否已经不够用？**  
   是「缺选项/缺糖」，还是「缺另一种协作关系」？前者扩现有包；后者才谈新能力。
2. **需求是否通用？**  
   多场景、可命名、可复现的并发协作需求 → 可进仓；一次性业务拼装 → 留在应用侧。
3. **是否值得扩展新能力？**  
   能收成新的范式接口（小表面 + 选项），且不与三轴重复、不滑向原语拼盘 → 才开新包或升格新轴。

只有 1=「缺协作关系」、2=通用、3=可范式化，才扩展；否则停在应用组合或现有包增强。

## 3. 双镜头：能力轴 vs 需求目录

两种整理方式互补，不互相替代：

| 镜头                   | 问法                                            | 用途                                                |
|------------------------|-------------------------------------------------|-----------------------------------------------------|
| **能力轴**（供给侧）   | 这个包约束的是哪一类协作关系？                  | 划包边界、定依赖方向、防变成原语拼盘                |
| **需求目录**（需求侧） | 我手头是哪种并发需求？该进哪个包 / 用哪些选项？ | 写 README / skill、做选型、发现「缺哪一类需求入口」 |

设计包时用能力轴；面对用户时用需求目录。

**需求句式不必 1:1 对应新范式包。** 同一能力轴下，常见落点有三层：

| 落点       | 含义                                               | 例子                                                                        |
|------------|----------------------------------------------------|-----------------------------------------------------------------------------|
| 范式包     | 新的协作心智 / 能力轴                              | 树形派生 → `nest`；任务编排 → `Scheduler`                                   |
| 选项组合   | 同一包上的策略拼装                                 | 串行+FIFO → `NewScheduler(job, WithParallel(1), WithFifoScheduleMode(), …)` |
| 具名构造糖 | 把高频选项组合收成名字；**仍是同一范式，不是新包** | `NewFifoSeqScheduler` ≈ 上式预置；`NewFifoScheduler` ≈ 并行+FIFO 预置       |

纪律：

- 糖函数 / 别名 **不新增能力轴**，只缩短高频路径
- 实现上应委托通用构造 + 固定选项，避免分叉两套逻辑
- 只有「选项怎么拼都说不清另一种协作关系」时，才考虑新范式包

## 4. 需求目录（场景 → 能力）

句式：`我有 …… 需求 → 范式包 | 选项组合 | 具名糖`

### 4.1 已具备

| 需求                                           | 落点                     | 说明                                                                           |
|------------------------------------------------|--------------------------|--------------------------------------------------------------------------------|
| 树形协程派生：父子同生共死、统一取消与优雅退出 | 范式包 `nest`            | 选项：shutdown timeout、before/after close                                     |
| 任务编排（总类）                               | 范式包 `schedx.Scheduler` | Push / Run / Close                                                             |
| 串行 + 先进先出                                | 选项或糖                 | `NewScheduler(…, WithParallel(1), WithFifo…)` → 可糖化为 `NewFifoSeqScheduler` |
| 并行 + 先进先出                                | 选项或糖                 | `NewScheduler(…, WithParallel(n), WithFifo…)` → 可糖化为 `NewFifoScheduler`    |
| 串行/并行 + LIFO                               | 选项或糖                 | 同上，换 `WithLifo…` / `NewLifo*`                                              |
| （已迁入）协程间传值/多播，可取消的订阅流      | 范式包 `pkg/chanx`       | `x/chanx` 已 archived                                                          |

编排轴上「串行 / 并行 / FIFO / LIFO」都是 **同一范式的组合**，不是四个包。

### 4.2 候补需求（依次类推 → 可能的新范式或升格）

| 需求                                            | 可能落点                | 备注                                   |
|-------------------------------------------------|-------------------------|----------------------------------------|
| 要一个「稍后才能取的结果」，并可 All/Race/取消  | Future / Promise        | 结果契约；非队列、非多播               |
| 要有身份的实体顺序处理自己的消息（地址 + 邮箱） | Actor                   | 比裸 Subject / 匿名 Scheduler 约束更强 |
| 主要表达「何时触发/截止/窗口」，而非如何排队    | Temporal（或先选项）    | 未升格前：`WithDelay` / job timeout    |
| 失败时要规定子树怎么处置（停谁、起谁、强度）    | Supervision（或先策略） | 未升格前：nest/Actor 的失败选项        |
| 多方必须到齐再进入下一阶段                      | Rendezvous / 阶段协作   | 低优先；勿直接暴露 Barrier 原语包      |
| 多阶段流水（A→B→C）或扇入扇出                   | 仍属**编排**            | 扩展 mode / 拓扑 API，不新立范式名     |

### 4.3 需求目录里不出现的（保持选项或排除）

「我需要一个令牌桶 / singleflight / 通用 queue」→ **不是**本仓需求入口句式；  
应改写成：「编排时要限流」「同 key 合并投递」「底层用 x 的容器」。

## 5. 能力轴（供给侧，当前核心）

```
生命周期 (who lives / when dies)   → pkg/nest
通信     (who talks / how signals) → pkg/chanx  （x/chanx archived）
编排     (who works / how queued)  → pkg/schedx (Scheduler)
```

| 范式     | 用户心智                         | 现状                                                                             |
|----------|----------------------------------|----------------------------------------------------------------------------------|
| 生命周期 | 谁在跑、何时算结束、如何优雅退出 | `Nest`：Spawn / Cancel / Parent·Children / shutdown timeout                      |
| 通信     | 谁跟谁说话、信号与订阅如何结束   | `pkg/chanx`：Observer / Subject；`x/chanx` archived                              |
| 编排     | 活怎么排队、怎么并行消化         | `Scheduler`：Push / Run / Close；FIFO·LIFO、pending、parallel、callback 等为选项 |

依赖方向：

```
nest, chanx          ← 低层
scheduler（及日后 pipeline 模式）← 中层，可依赖低层
hooks（若有）           ← 横切选项，不单立范式
```

### 5.1 关于 `x/chanx`（已 archived）

- 规范路径：`github.com/xoctopus/concx/pkg/chanx`
- `x/chanx` 保留兼容，标注 ARCHIVED / Deprecated， **冻结**、不新增功能
- 与 Scheduler： **组合**（Observe → Push），不合成一包
- 新代码请直接依赖 concx；旧调用方择机迁移

### 5.2 当前编排选项（备忘）

| 选项                                            | 角色                        |
|-------------------------------------------------|-----------------------------|
| `WithMaxPending` / `WithoutPendingLimitation`   | 排队背压                    |
| `WithParallel`                                  | 并行度                      |
| `WithFifoScheduleMode` / `WithLifoScheduleMode` | 排队模式（可扩展更多 mode） |
| `WithCallback` / `WithExitCallback`             | 完成与退出钩子              |
| `WithCloseTimeout`                              | 关闭等待                    |
| `WithoutDetached`                               | job 是否跟随取消            |

## 6. 同级候补范式（能力轴视角）

与「编排 / 生命周期 / 通信」同级；细节需求句式见 §4.2。

### 6.1 异步结果（Future / Promise）— 优先

延期结果契约；选项：超时、取消、panic→error、detach。

### 6.2 Actor — 优先

实体 + mailbox + 行为；选项：容量、溢出、监管关系。

### 6.3 时间（Temporal）— 可先选项后升格

升格条件：用户主要表达时间关系。否则留在编排/生命周期选项。

### 6.4 监管（Supervision）— 可先策略后升格

升格条件：需要显式监管树，而非一次 Cancel + 回调。

### 6.5 汇合 / 阶段 — 低优先

场景不够清晰前不做；勿对外裸露 Barrier。

## 7. 明确不当成新范式

| 能力                                           | 处理                           |
|------------------------------------------------|--------------------------------|
| 限流 / 令牌桶 / 信号量                         | 编排或通信的背压 / 准入选项    |
| singleflight / 按 key 合并                     | 编排选项（或 Actor 邮箱策略）  |
| FIFO / LIFO / priority / pipeline 拓扑         | 编排的 `mode` / 拓扑选项       |
| 串行执行                                       | 编排选项（parallel / pending） |
| before/after close、shutdown timeout           | 生命周期选项                   |
| 缓冲大小、丢弃/阻塞、完成错误                  | 通信选项                       |
| metrics / 探测 hook                            | 横切选项                       |
| 通用 queue/stack/map                           | 留 `x`                         |
| 分布式调度 / 跨进程队列 / BPM / 完整 Rx 算子库 | 排除                           |

## 8. 演进优先级（建议）

| 优先级 | 事项                                                    |
|--------|---------------------------------------------------------|
| 当前   | 三包齐：nest / schedx / chanx；需求目录进 README / skill |
| 高     | Future vs Actor 择一（对接薄选 Future；叙事强选 Actor） |
| 中     | 编排增加 mode（priority / 简单 pipeline）；具名糖       |
| 中     | 时间、失败策略先以选项长在现有包上                      |
| 低     | 监管树升格、汇合阶段、测试假时钟 / synctest 辅助        |

扩展需求目录时的检查：

1. 先走 §2.1：三包范式 API → 选项 → 糖
2. 仍不够 → 三问：不够用？通用？可范式化扩展？
3. 通过三问再开新轴 / 新包；否则留应用侧或只增强现有包
